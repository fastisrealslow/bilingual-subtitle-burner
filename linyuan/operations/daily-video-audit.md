# 林园：每日 17:00 最近四条视频巡检与通用修复

这是用户授权的每日自动任务，仓库 fastisrealslow/bilingual-subtitle-burner。
使用当前提供的隔离工作区，沿用已登录的 GitHub 连接和本机 Codex 配置。
用户要求：逐条检查最近发布的 4 个视频和当天 bug，发现问题后查清根因，
通过通用、自动化的方式修复，自测通过后上线。不要因任务是定时启动而只写建议。

## 确定范围

- 从最新 main 的真实发布回执和 B 站公开状态核实最近 4 个不同 BVID。
  不是最近四个素材、四个生产任务，也不限于今天；17 点可能含昨天 21 点的视频。
  运行目录中的 selected-videos.json 只是初选回执，不代表已核实公开可播放。
- 对不足 4 条、缺少回执、无法核对公开状态或取不到成片分别记录“未完成/待确认”，
  不得用旧缓存、原始母片或模型自评替代真实发布版本，不得标成“没问题”。
- 查看最近 24 小时 Actions、部署、生产、字幕、上传、定时发布和库存错误。
  对重复问题归类，区分代码故障、素材限制、网络和账号/余额故障。

## 逐条检查

1. 核实公开链接、标题、封面、投稿时间、文件身份/版本、横竖画幅、时长及重复发布。
2. 获取实际发布版本或能证明与发布文件一致的产物。检查全片音视频解码、缺音、
   截断、黑屏、音画同步、异常静止；观看封面和开头、中段、结尾、转场的实际画面。
3. 检查字幕错字/人名/数字/否定词、断句、时序、遮挡、越界及原生字幕冲突。
   对照音频和源文判断；未听完、未看完或缺少工具时明确检查覆盖范围。
4. 检查标题和封面是不是完整自然、具体、吸引人的观点，是否忠于林园原话，
   是否误把主持人的问题当结论，是否夸大收益、删掉条件或留下半句话。
5. 检查开头是否迅速进入观点、论点和例子是否完整、转场和结尾是否自然。
   横竖版分别按实际画面验收，时长按内容完整性判断，不强行凑 120 秒。
   对照仓库中园园滚雪球的基准材料；若取到了最新参考视频，记录实际观看依据。
   不能声称只凭播放率、截图或模型分数就与园园质量持平。

## 通用修复与上线

- 先复现并定位共性原因，再修改选段、字幕、标题、封面、渲染、下载、发布或调度的通用逻辑。
  不新增按 BVID/素材 ID/日期/单句标题分支的生产补丁，不手写某一条的“通过”结果。
  真实失败样本可以作为回归测试，但必须同时验证同类变体和正常反例。
- 在隔离分支修改，不覆盖主工作区未提交内容、线上库存、发布历史或回执。
  使用已有 GitHub Actions 做重型媒体/模型验证，本机以调度、检查、修复为主。
  保持原文证据和质量门槛，不能靠放宽门槛、伪造验收或多发低质视频提高成功率。
- 运行针对性测试与项目必要回归；涉及文案/画面时验证真实产物，涉及工作流内嵌代码时检查其语法。
  测试和评审证据充分后提交 PR、合并、走已有生产部署及健康读回流程。
  用户已授权本范围内的通用修复和自测后上线，无需例行再问一次。
- 保留 GitHub 调度和 FC 节费设置。巡检本身不重发、删除、改写历史已发布视频，
  不绕过发布配额、去重、审核或账号权限；账号/余额问题要准确报告，不能伪装成素材不合格。
- 没发现可证明的问题就不改代码；证据不足的修改不强行上线。

## 报告

在运行目录保存证据，最终用中文逐条报告 4 个视频：链接、标题、检查覆盖范围、
发现的问题与严重程度、截图或日志位置、根因、通用修复、测试、PR/部署链接和剩余限制。
没有完成实际检查的条目必须保留为待确认。区分“任务执行完成”和“视频全部通过”。
最后说明今天是否发现新 bug、是否已修复上线、还有什么阻塞；保留工作区供追溯。
